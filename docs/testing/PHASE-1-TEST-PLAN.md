## TP-01 — Baseline and proposed harness

No automated tests/test script or runner configuration currently exists. The supplied prior `npm run lint`, `npx tsc --noEmit`, `npm run build` and migration-status results remain historical evidence. Static checks do not prove session revocation, database isolation, overlap protection or business ID concurrency. The reported six audit vulnerabilities remain open. No database or authentication request was made in Phase 1A.

For the smallest future harness, use Node's built-in test/assert facilities with the already installed `tsx` TypeScript loader for pure/service tests, subject to a compatibility smoke check in the implementation phase. Use the real Prisma 7/MariaDB-adapter path against an isolated database matching the selected deployment engine/version for relational, transactional, collation and concurrency tests. In-memory maps and SQLite do not substitute for these tests. Browser-level login/logout tests need a separately reviewed automation harness; do not install one or change package files in this phase.

Node's built-in runner is documented in the [Node 24 test-runner reference](https://nodejs.org/docs/latest-v24.x/api/test.html). That moving documentation may describe a newer Node 24 patch than this repository's verified 24.19.0; verify only the APIs actually used against the installed runtime before implementing the harness.

Proposed future files: `tests/foundation/unit/authorization.test.ts`, `history-ranges.test.ts`, `policy-gates.test.ts`; `tests/foundation/integration/ownership.test.ts`, `auth-session.test.ts`, `role-mapping.test.ts`, `employee-identity.test.ts`, `history.test.ts`, `audit.test.ts`, `migration-preservation.test.ts`; `tests/foundation/e2e/login-logout.test.ts`; and shared fixture/clock/database helpers. These paths do not exist as deliverables now. Unit acceptance examples must have independently specified expected outcomes, not assertions copied from implementation branches.

Example future unit command after the file/harness exists: `node --import tsx --test tests/foundation/unit/authorization.test.ts`. Integration and browser commands must be documented exactly when their harness is implemented; no invented `npm test` pass is recorded here. Any necessary development dependency or package-script changes belong to a later authorized implementation batch.

## TP-02 — Isolated fixtures and execution safeguards

- Provision a uniquely named, disposable test database with an explicit allowlisted test endpoint/name and restricted test-only principal. The harness must refuse missing/ambiguous target identity or any normal application database target; no silent fallback to configured production credentials. Do not use production reset, destructive DB push, seed or real administrator bootstrap.
- Fixtures represent two tenants, at least two companies in the first tenant and one company in the second. Include identical display names and overlapping local codes where new constraints allow, but distinct preserved global employeeCode values. Test IDs are synthetic. Include active/inactive/locked/suspended users, the seven approved role templates, four legacy roles, extra custom role/permission rows, scoped memberships and unlinked users.
- Include an existing synthetic administrator with a valid legacy bcrypt hash and old-format JWTs; a valid Argon2id credential; malformed/unknown hash formats; short, boundary-length and multibyte credentials generated in memory. Never use/copy the real administrator's hash, password or session secret. Persist only test-required artifacts in the disposable environment; sanitize CI output and browser traces.
- Include valid canonical NBSE codes with gaps, noncanonical legacy codes, reserved IDs, archived employees, known/unknown exit dates, contradictory same-day salary facts, mismatched current salary, inactive masters and unknown assignment dates. Record expected preservation values independently of the migration code. No fake personal data is inserted into the real database.
- Inject a controllable clock into services to test UTC instants and date-only Asia/Karachi business dates without long sleeps. Concurrency tests use independent DB connections/processes and synchronized request start/fault hooks, not a single serial connection or barrier held while waiting for the same row lock. Run enough callers to exceed the service connection pool and exercise retries; record actual concurrency and isolation settings.
- Replay the two existing migrations into a fresh isolated database, populate the legacy fixtures, then apply proposed migrations/backfills in the exact planned batches. Also rehearse on an access-controlled representative restore where approved; no personal data is copied into repository fixtures or public CI logs.
