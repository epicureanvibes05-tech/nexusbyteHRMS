## D-02 — Shared data contracts

These contracts form part of **every model/change card** below, including legacy tables. Model cards supply purpose/relationships, constraints/indexes, scope/privacy/history, migration impact/rollback risk and requirement references. All relationships use existing IDs without resequencing them.

- Company-owned records carry `tenantId` and `companyId`. Company has a unique `(tenantId, id)` key; owned parents have `(tenantId, companyId, id)` keys. Child references use the complete owner tuple, not an ID-only FK. Tenant-owned User has `(tenantId, id)`. Catalogue rows with global scope are explicitly identified and contain no company data.
- Index every referencing owner tuple and common query prefix `(tenantId, companyId, ...)`. Foreign keys prevent contradictory ownership; server authorization prevents an attacker choosing another valid owner tuple. Neither replaces the other. Unknown/null ownership during backfill is quarantined from new protected reads, never treated as global access.
- Authentication timestamps and audit timestamps are UTC instants. Business history uses date-only `[validFrom, validTo)` ranges in the recorded company timezone; null end means open-ended. Adjacent ranges are allowed. Preserve old date values exactly and record timezone provenance. This is a proposed interval convention, not approval of payroll-cycle boundary semantics under OD-05.
- Use fixed decimals for money; no new currency conversion or salary arithmetic. Non-money IDs/counters are integral, bounded and overflow-checked. No pseudo-personal data is created to fill missing fields.
- Historical references use RESTRICT, not cascades. No ordinary deletion of employees, users, roles, grants, issued IDs or historical financial rows. Administrative retention/deletion is a separately approved OD-15 workflow with legal hold; this design does not grant perpetual retention authority.
- Every write has an authenticated actor or identified migration service actor, request/correlation ID, idempotency key where retriable, safe reason code and protected evidence reference where required. Evidence references are typed internal identifiers for an authorized source or protected migration manifest, not arbitrary URLs, access tokens or file contents.
- `createdAt`/`recordedAt` prove recording time, not an invented business effective date. Imported facts carry `sourceKind=LEGACY_IMPORT`, source record ID and batch reference; unknown creator/approver/date stays unknown. Review of an import does not fabricate historical registration approval.

## D-03 — Server authorization boundary

Resolve request → verified session → active User → Tenant → explicitly active UserCompanyAccess → action permission and organization scope → field projection → database operation → safe response/audit. Tenant configuration actions may use a tenant assignment without company context, but company-data access always requires an explicit company membership. Never infer company from an untrusted request ID or accept a client-supplied role/permission list. Reload authority on each request; do not trust role arrays returned by the old login response.

Use a server-only data access layer returning minimal DTOs; protected pages, route handlers, background jobs and future APIs share that boundary. Scope lookup, update target and referenced parents in the same transaction for mutations; include owner predicates even after a prior check. Aggregate counts, lookup options, search, errors, nested writes and exports are data access too. Do not cache protected data across identities; request-local caching must be keyed by the validated context. The installed Next.js guides at `node_modules/next/dist/docs/01-app/02-guides/data-security.md`, `authentication.md` and `01-app/01-getting-started/15-route-handlers.md` were consulted for DAL/session/route boundaries; no application code is written here.

### Credential transition without invalidating the administrator

Deploy and verify a dual-format verifier before enabling any Argon2id writes. Keep existing User IDs, email/username matching, activation/lockout state, role records and bcrypt hashes untouched by migration. Recognize supported bcrypt/Argon2id encodings; reject malformed/unknown hashes safely. The old bootstrap script is not used to test or recover this transition.

On successful bcrypt verification, compute an Argon2id replacement in memory outside the short database transaction. Recheck active/locked state and `credentialVersion` under a User row lock, then conditionally replace the exact old hash/version; a concurrent password reset wins and prevents session creation with stale credentials. A concurrent successful rehash can be reconciled by re-verifying the now-current hash; never overwrite it blindly. Increment credentialVersion for representation changes, but do not falsely advance passwordChangedAt or global sessionEpoch merely for a hash upgrade. Genuine password change/reset advances the credential version and revokes all prior sessions. Failed login never rewrites a hash. Hashing failure keeps the valid legacy hash and uses the deliberately bounded compatibility policy with a sanitized security event; it must not reset, reactivate or lock out the administrator as a migration side effect.

New/reset passwords use Argon2id once enabled. Choose the implementation package only after verifying Node 24 and Hostinger runtime support and benchmarking memory/concurrency; no dependency is selected or installed here. The technical starting benchmark is Argon2id memory at least 19 MiB, two iterations, parallelism one, then stronger settings if capacity allows; this is not an unreviewed application policy. Bcrypt's 72-byte boundary requires special handling, also confirmed by installed `node_modules/bcryptjs/README.md`. On a verified legacy input at or above 72 UTF-8 bytes, retain bcrypt compatibility and require an explicit authenticated credential replacement before full-input Argon2id conversion; do not silently bind a previously unverified suffix. Test multibyte boundaries and older long credentials. [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

No bulk hash conversion is possible without a verified password, and no migration requests or records one. Keep the inactive legacy-account population on bounded migration tracking until later approved reset/retirement, not a forced guessed password.

### Persistent sessions, legacy cookies and state semantics

New cookies may retain the current name and jose signing mechanism, adding a format version, random session ID and nonce; Session stores a digest of the complete token. JWT claims contain no permissions or sensitive fields. Signature validation is followed by database state, expiry, user status, epochs, membership and effective employment-status checks. A cryptographically valid cookie alone is insufficient.

The compatibility release records a deployment cutoff and stops minting old-format JWTs. Until at most cutoff plus the existing eight-hour maximum lifetime, validate old-format issuer/audience/signature, iat/exp, subject and user state; reject tokens issued beyond cutoff or with excessive lifetime. Atomically materialize one Session row keyed by a token fingerprint on first use, preserving its original expiry and recording that pre-cutover activity is unknown. The same fingerprint row is looked up thereafter: logout/revocation must never permit rematerializing it as active. Identical old JWTs may represent multiple browsers because the old code lacks nonce/jti; treat them as one legacy token identity and document that limitation. Expired/unknown historical sessions cannot be reconstructed.

Legacy logout also materializes-and-terminates a valid previously unseen token atomically. User-level `sessionsRevokedBefore` (full-precision UTC) rejects old tokens issued at or before a reset/suspension/revocation boundary, including unseen ones; conservatively reject boundary-second legacy tokens rather than guessing order. Old signatures have a dedicated bounded verification path; keep verification material protected until the window closes, then disable that path. This cannot preserve revoked sessions, but it preserves valid credentials and avoids an unnecessary mass logout. Company membership and reviewed authorization apply even to legacy cookies.

| Required display state | Proposed stored state / transition | Meaning and evidence |
| --- | --- | --- |
| active | ACTIVE on successful issuance/materialization | Usable only while all online checks hold |
| logged out | LOGGED_OUT on explicit logout | Exact server-observed action time; cookie cleared after durable termination |
| expired | EXPIRED when absolute lifetime ends | Expiry enforced by timestamp on every request, independent of cleanup job |
| revoked/forced | REVOKED with reason such as ADMIN, PASSWORD_RESET, SUSPENDED, EXIT, ROTATED | Administrative/security termination; rotation links successor; never reactivate old row |
| abandoned | ABANDONED at an approved inactivity cutoff without observed logout | Inferred inactivity, not known browser-close/logout time; store inference time and lastSeen separately |

If no separate inactivity policy is approved, do not invent abandonment times: inactive sessions reach EXPIRED at absolute expiry. A scheduled sweep materializes terminal state for reporting; authorization already denies elapsed deadlines. Competing transitions lock the Session row; first terminal event is preserved and later actions are separate audit events. Reinstatement/rehire never changes terminal sessions back to ACTIVE.

Rotate identifiers on authentication, privilege elevation and approved renewal; revoke obsolete sessions on permission reduction, membership revocation, password reset, deactivation, suspension and effective exit. Renewals create one new child in a transaction and terminate predecessor with ROTATED reason; do not extend original family absolute expiry. Concurrent renewals have one winner; stale requests are rejected without clearing a potentially newer browser cookie or minting multiple children. No rolling grace acceptance of revoked tokens. Lost response requires safe reauthentication. Browser-close is not a reliable logout signal. These rotation/revocation choices follow [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Apply session cookie writes/deletes in route handlers or other supported mutation contexts; server rendering does not silently rotate cookies. Keep the old cookie readable during its bounded window without requiring a redirect migration. Logout persistence failure must be reported as failure, never a false durable-logout success; best-effort browser clearing alone cannot revoke a stolen token.

### Lockout, reset, MFA and request protection

Serialize counter updates using the User row and apply the selected policy consistently across replicas; independent identifier/network rate limiting must also protect unknown users. Preserve existing lockedUntil and counters on backfill. Record generic client errors while distinguishing internal invalid credentials, blocked/rate-limited, locked and successful outcomes. Do not place raw identifiers, IPs, user agents or error objects in generic audit. Define bounded failure-handling for attempt persistence: deny issuance on durable-record failure and send only sanitized operational alerts; no silently untracked successful login.

Reset request responses must not disclose account existence. Verify delivery identity using an approved channel, create hashed one-time challenge, and on consumption atomically change password, consume challenge, clear/reset policy-controlled counters and revoke prior sessions/challenges. No automatic login from the request endpoint and no administrator bypass using knowledge of an email address. An operator-assisted recovery path requires identity verification and audit; it is not the current password-overwriting seed. MFA is architecture capability only: no requirement/enrollment switch activates without explicit approval, tested recovery and OD-16 key handling.

For cookie-authenticated mutations, including login/logout/reset/renewal: validate an explicitly configured origin against the deployment origin, enforce intended JSON/content types, reject untrusted/missing origins except a deliberately authenticated non-browser integration path, and use a session-bound anti-CSRF token for authenticated mutations. Pre-login/reset requests use bounded pre-auth CSRF protection plus origin validation. Do not infer trust from arbitrary forwarded headers; hosting proxy configuration is OD-17. SameSite is defense in depth, not the complete control. Add safe error responses and allowlisted logging in the future service slice.

### Organization scope semantics

| Scope | Resolution and boundary |
| --- | --- |
| self | Verified Employee link in selected company; no email/name matching |
| direct reports | Current effective primary reporting line only, not recursive reports or every historic report |
| team | Explicit same-company team anchor and effective memberships; team-lead title alone grants nothing |
| department | Explicit Department anchor and current effective assignment |
| branch | Explicit Branch anchor, with validated location-parent relationships |
| company | Selected company and active membership; no sibling companies |
| tenant | Tenant configuration only by default; company-data actions still require explicit company allowlist/memberships and the relevant data/field grants |

Historical team access is not automatically retained when a manager changes. Foundation default for ordinary manager access is current relationship plus allowed field view; access to prior-team history needs an explicit history permission and approved scope. All scope kinds are modeled now; unavailable/unknown organization assignments resolve to denial until verified data exists. Grants use effective dates and server time, with scoped cache invalidation on access changes.

Sensitivity is Normal, Confidential, Sensitive or Highly Sensitive as in §3.1. A sensitivity tier is a ceiling, not blanket access: explicit fields/actions remain required. Separate salary-view from salary-change/approve; CNIC-mask from CNIC-decrypt; document-metadata from download; employee-view from bank/tax/medical/grievance. Field-level write validation rejects extra keys. Hiding a field in UI does not prevent it from being fetched or exported, so selection and serialization must both enforce the rule.

In an empty namespace, counter starts at `NBSE-0000`; the first committed issued ID is `NBSE-0001`. Padding has a minimum width of four, not a rollover at 9999. Namespace prefix NBSE is reserved for this tenant; no second tenant silently reuses it. Existing global employeeCode uniqueness remains until a separately reviewed namespace change.

Issuance transaction: authorize registration approval and freeze its version; lock the registration/target Employee if any; return the same allocation for an already completed idempotency key; lock the sequence row; advance to the next non-reserved serial; create allocation and Employee (or assign canonical businessId to the verified legacy Employee); commit approved registration linkage and audit in the same transaction. Return/display the ID only after commit. Deadlock/conflict retries are bounded and reuse the idempotency key. Never use `MAX + 1` at runtime, row count, timestamps or client numbering. Locking a counter before incrementing it is supported by [MySQL locking-read guidance](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html); exact target-engine behavior must be rehearsed.

Only committed/publicly issued IDs count as issued. Rolled-back unseen work may reuse its uncommitted candidate; any externally reserved/disclosed ID must first have a committed allocation and is burned if later abandoned. Backup recovery must preserve/replay the high-water mark and issued ledger so a previously disclosed ID is not reissued.

Before backfill, classify existing codes: valid canonical NBSE, noncanonical legacy, malformed/reserved/duplicate-normalized candidates and unknown historical issuance. Preserve `employeeCode` unchanged in every case. Valid canonical codes can populate businessId/allocation under explicit migration-adoption approval, recording original approval as unknown if unavailable. Noncanonical codes remain usable legacy identifiers; new businessId issuance requires authorized adoption/registration review and does not rewrite the old alias. Collisions or unverifiable prior issuance block only new namespace issuance until reconciled. Rehire uses the same Employee/allocation and a new employment period, never a new ID or restored old permissions.

## D-07 — Effective-dated history and archive

Use typed histories with an append-only **complete employee history revision**. A revision contains the effective period, assignment, reporting and salary interval sets for one Employee. On change, append a new revision with copied unchanged facts and revised interval sets, then atomically advance Employee.currentHistoryRevisionId; all prior rows remain addressable. This deliberately favors simple, reviewable consistency over storage optimization for the initial workforce. It avoids rewriting a published end date, and supports an as-recorded revision independently of business effective time. No mutable JSON event store is proposed.

All history rows carry revision, period, owner and Employee references with composite constraints proving they belong together. A nullable unknown end cannot mean a fabricated termination: unresolved imported period validity is flagged and is not eligible for payroll/rehire activation until reviewed. Do not copy sensitive history into generic audit; keep protected domain tables as evidence.

Reject overlap where `existing.from < proposed.to` and `proposed.from < existing.to`, treating a valid open end as infinity. Evaluate within Employee/current revision/period/domain (and component or reporting-line kind as applicable); earlier superseded revisions naturally overlap and are not conflicts. Date-only boundaries are tested independently of UTC audit times. A unique start date alone does not prevent overlap.

Concurrency: every history writer locks the stable Employee row before reading/publishing its latest timeline; competing requests revalidate after waiting. Do not rely on a read-then-insert check without a common lock or on PostgreSQL-only exclusion constraints. Reporting graph updates additionally lock the Company row first to serialize checks across employees; check for cycles over every affected effective interval, not only today's graph. Cross-company graph edges are rejected. All writers, including imports and repair tools, must use this protocol; any future direct-write integration needs equivalent controls and tests.

Status authorization uses the effective assignment and membership state on every request. A future suspension/exit is denied from its effective boundary even if a scheduler is late; a sweep then records revocation state. Immediate suspension/deactivation commits status/epoch and session termination with audit atomically. Reinstatement requires new login and explicit access review. Posted/paid downstream records cannot be recalculated implicitly after a retroactive revision; preserve their original version and emit an impact-review reference for the later payroll workflow.

## D-08 — Pending policies and sensitive data

Preserve all seven legacy booleans and their baseline values. The future runtime predicate is explicit employee eligibility **and** approved, effective company policy version **and** required legal/individual approvals. Unknown approval means no automatic deduction and an explicit pending-policy exception, not silent zero-valued payroll approval. New defaults become false only after compatible policy-aware writers are deployed; changing defaults alone does not fix existing true values. OD-01–14 continue to gate related financial behavior. Label affected rules **Company Policy — Legal Review Recommended**.

No final encryption implementation is asserted while OD-16 is open. The later protected-field contract must define ciphertext/version/key ID/authenticated metadata, authorization before decryption, masked DTOs, rotation/recovery and safe search. CNIC uniqueness cannot be maintained by random ciphertext comparison: review a company-scoped keyed equality index and normalization/collision process without logging the identifier, or explicitly prohibit exact lookup until designed. Do not use a plain unsalted hash of a predictable identifier as confidentiality protection. Preserve the current CNIC uniqueness constraint during this phase; widening it is a separate migration decision. Sensitive data migration, plaintext retirement and backup key access require an approved OD-16 design and restore proof.

M-32 — Sensitive-field access/encryption change: purpose is protecting identity/contact/salary and later bank/tax fields; relationships remain Employee/domain records with same-owner keys; indexes only for approved protected lookup patterns; scope is field/action plus company. Effective corrections retain protected history, not generic old/new values. Migration is additive ciphertext/key-version columns and verified protected backfill in a later gated slice, followed by separately approved plaintext retirement. Rollback cannot discard keys/ciphertext or re-expose plaintext; after encrypted-only writes, old plaintext readers are not a recovery option. References §§3.1, 5.2, 5.4, 24, 29.15–16. This card is a design boundary, not permission to invent an encryption provider.

## D-09 — Append-only audit and security evidence

M-33 — **AuditEvent**: purpose is durable business and security evidence. Relationships include authenticated actor User, optional subject, tenant/company context, Session reference, request/correlation ID, source revision/entity reference and typed reason/evidence reference. Unknown pre-auth events may have no resolved tenant/company and are visible only to security operations. Composite references validate resolved owners; they never trust a user-supplied owner claim. Key constraints: immutable event ID; unique event/idempotency key per operation; schema-versioned allowlisted metadata; valid category/action/outcome. Indexes: owner/time/id for pagination, owner/entity/time, actor/time, correlation ID and session reference. Privacy: only safe changed-field names, record/version IDs and reason codes; no password/hash/token, full CNIC/bank/tax/address/contact, salary amounts, medical/grievance text, raw bodies or raw exception objects. History: append-only events, corrections reference prior event. Migration impact: F1 additive table/writer; no fabricated prior audit rows. Rollback risk: retain newly recorded events and writer compatibility; never delete evidence to hide a reverted business operation. References §§2.1, 23–24, 28, 31.

A separate **SecurityEvent table is not justified for the smallest slice**: use `AuditEvent.category=SECURITY` with security-only access and approved retention partitioning. LoginAttempt is separate because high-volume attempt analysis and unknown-user throttling have different fields/access needs. Each successful security operation creates its required session/attempt/event records consistently; identifiers correlate them without duplicating sensitive values. A later separate security sink/table requires concrete retention/access/scale justification, not duplicate generic JSON.

Business mutation and its audit insert share a transaction; if the audit insert fails, the mutation fails. Failed/denied requests are recorded in a separate bounded transaction so rolling back a failed mutation does not erase the denial record. Security logging outage denies sensitive writes/login issuance and raises sanitized operational alerting; never a fallback containing a request dump.

The application DB principal may INSERT audit records and SELECT only through restricted service paths; it must not UPDATE/DELETE them. A distinct migration/retention principal is held outside ordinary app execution. Ordinary users have no mutation endpoint and no raw database access. Privileged DB operators can still alter storage, so append-only application behavior is not a claim of tamper-proof protection against the DBA. Before production, verify grants and independently protected backup/log evidence; OD-15 governs later legal deletion/hold handling. No cascade from User/Employee/Company to audit.
